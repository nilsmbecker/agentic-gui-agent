# Agentic AI — Day 2 lab: build the context

In this lab, you will assemble the context sent to a local model: tool calls
and results, stable prompt prefixes, Skills, agent status, and persistent
memory. You will inspect the requests, change the examples, and explain how
those changes affect what the model can see.

The scripts use Python's standard library. No SDK or pip install is needed.

## Before you start

Use Python 3.10 or later. Open a terminal in this `D2` directory and run all
commands from here. Start the Ollama app or run `ollama serve`, then inspect
the installed models and check your setup:

```bash
ollama list
python3 check_setup.py
```

The default model is the local `qwen3-vl-4b:latest` tag, with Ollama at
`http://localhost:11434`. `common.py` also accepts the official `qwen3-vl:4b`
tag when the local tag is absent. If neither is installed, run
`ollama pull qwen3-vl:4b` before checking your setup.

All four steps share this model selection. `OLLAMA_MODEL` overrides the
default; use `unset OLLAMA_MODEL` to remove an earlier override. Step 1 also
accepts `--model`, which takes precedence over the environment variable.
The first model request may take longer while Ollama loads the model.

## The four tasks

1. Construct a tool-use conversation and identify its components.
2. Measure how the position of changing information affects prompt processing.
3. Load a Skill on demand and include code-maintained status in a request.
4. Save persistent preferences and reload them into a new conversation.

```bash
python3 step1_tool_context.py
python3 step2_prefix_cache.py
python3 step3_skill_status.py
python3 step4_memory.py
```

## What you do in each step

### Step 1 — let the model call a tool

Open `step1_tool_context.py`. The script sends the initial request and lets
the model generate `assistant.tool_calls`. Python validates and executes
`multiply`, appends the result, then sends the updated conversation back to
the model for its final answer. All assistant messages come from the model.

Step 1 requires native Ollama tools support. It uses the same 4B default as
the other steps and checks that the selected model advertises `tools`.
Override this with `--model <tag>` or `OLLAMA_MODEL`; an unsupported model
produces a clear error. `--dry-run` previews only the first request, with no
model reply or tool execution. `--max-rounds` bounds the number of model
requests (default: 4, including the final answer).

1. Run the script and locate the system prompt, tool definition, assistant
   tool call, and tool result in the printed requests.
2. Find the arguments `a` and `b`, then find the matching `tool` message.
3. Change the integers in `USER_TEXT`. Run again and inspect the arguments
   generated by the model and the result computed by Python.
4. Inspect `artifacts/step1.json` and trace how the result reaches the model.

Be ready to explain which part the model generates and which part Python
executes. Both requests are sent and recorded: the second contains the actual
assistant tool call and its result. The loop also handles multiple calls and
returns tool errors so the model can correct its arguments. If the model
never calls a tool, returns an invalid reply, or exhausts the request limit,
the run stops with a nonzero exit code and preserves the diagnostic record.

### Step 2 — measure a stable prompt prefix

Open `step2_prefix_cache.py` and inspect `messages_for()`. The `early` layout
places a changing status revision before the reference text; `late` places it
after the reference text. Each measurement immediately follows its own warm
request. Within that pair, only the revision changes.

1. Run the script. By default, it measures each layout three times and
   alternates their order.
2. Open `artifacts/step2_measurements.csv` and compare `prompt_eval_ms` for
   `early` and `late`, including the medians printed in the terminal.
3. Use `artifacts/step2.json` to compare a warm request with its measured
   request. Identify the unchanged prefix and the changing field.
4. Explain whether your measurements show faster prompt processing with the
   longer stable prefix. Report the observed result, including no speedup.

### Step 3 — load a Skill and maintain status

Open `step3_skill_status.py` and
`skills/three-bullet-summary/SKILL.md`. The function `should_load_skill()`
checks for `three bullet` or `3 bullet` in the user request, ignoring case.
When the trigger matches, Python loads the Skill file into the system message.
It also includes a status dictionary in a separate user message.

`build_request()` only builds the request and captures a status snapshot;
it does not increment counters or contact Ollama. `call_model()` increments
`model_calls` immediately before attempting to send a chat request (failed
attempts count too). The request carries `phase="calling_model"`; Python then
sets its local phase to `completed` or `failed` and prints the final status,
including the error on failure. Request construction failures do not increment
the counter. Model and host selection use `common.py`.

1. Run the supplied request and locate the loaded Skill and `<agent_status>`
   in the printed `NEXT REQUEST`.
2. Compare the status sent to the model with the final status printed after
   the reply. Identify where Python updates each field.
3. Change `user_text` to a request that does not match the trigger. Run again
   and compare the requests.
4. Edit a procedure in the Skill file and try another matching request. If
   you change the trigger wording, update `should_load_skill()` accordingly.

Be ready to explain how Python decides to load the Skill, what the Skill adds
to the request, and who maintains the status. Each run starts with a new
status dictionary.

### Step 4 — save and reload memory

Open `step4_memory.py`. The sample conversation includes lasting preferences
and a temporary reference code. The script asks the model to extract
preferences and prints its answer as `Extracted memory`. The separate
`memory` dictionary in the code supplies the facts saved to disk.

1. Run the script and compare the model's extraction answer with the provided
   `memory` dictionary. Identify which facts should persist and why the
   temporary reference code should be excluded.
2. Open `artifacts/memory.json` and check the saved preferences. Trace the
   code that writes the dictionary and reads it back.
3. Compare the replies under `Fresh session WITHOUT memory` and `Fresh
   session WITH memory`. Inspect the `without_memory` and `with_memory`
   message lists to see what information each request supplies.
4. Change one persistent preference in `conversation` and make the matching
   change in the `memory` dictionary. Run again and explain the result.

Be ready to explain why saving a file alone does not give the model access
to its contents. The application must load the facts and include them in a
new request. Both comparison requests use new message lists within the same
script run.

## Outputs

| Step | Where to inspect the result |
| --- | --- |
| 1 | Terminal output and `artifacts/step1.json` |
| 2 | Terminal medians, `artifacts/step2.json`, and `artifacts/step2_measurements.csv` |
| 3 | Printed request, model reply, and final status in the terminal |
| 4 | Printed extraction and comparison replies, plus `artifacts/memory.json` |

The scripts create `artifacts/` when needed. Rerunning a script replaces its
generated files. Copy files and save relevant terminal output before another
run if you want to keep comparisons. Keep your observations and outputs for
the individual oral check.

## Supporting files

- `common.py` provides the shared Ollama client used by the setup check and
  steps 1–2, plus model selection and host configuration for step 3.
- `lab_support.py` handles request construction, timing, printing, and logging
  for steps 1–2.
- `skills/three-bullet-summary/SKILL.md` provides the procedure loaded in step 3.

Keep these files with the exercise scripts. You can complete the tasks by
editing the step scripts and the Skill file.

Protocol reference: [Ollama tool calling](https://docs.ollama.com/capabilities/tool-calling).
